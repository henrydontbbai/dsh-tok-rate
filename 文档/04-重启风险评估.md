## 1. 直接回答

**Q1：重启后是否还会有报错的风险？**
一句话：**宿主几乎不会因此报错；插件半有明确但可控的降级风险。**
最关键证据：宿主启动审计 `auditStartupEntries()` 对「非必需条目」只打一条 warning 后继续放行并保留其余插件（`app.asar` @22051690-22052200：`if (failures.length > 0) warn(activationDiagnostic(binName, failures));`）；必需清单 `requiredStartupEntryIds` 只含 `agent-loop / webserver / web-runtime / modules / connection / headless-runner / acp / sdk-jsonrpc-server` 八项（@22044494），**`dsh-tok-rate` 不在其中**。官方 bootstrap README 同口径："With that entry point, startup keeps every plugin that can activate. An enabled failed plugin produces a labelled warning."（@21786439 附近）。

**Q2：是否可能直接起不来（宿主崩溃 / 无法启动）？**
一句话：**不会**。坏在这一行上的唯一后果是该插件被跳过、宿主继续启动；"整机起不来"的通道（必需条目失败 `StartupError`、或 `installFailLoud` 的未处理拒绝）在本插件启动路径上够不着。
最关键证据：① profile 装载器 `loadProfileDirectory()` 对 `dsh.profile.bundles` **每一项**做 `try/catch`，抛错就 push 进 `skippedBundles` 并继续（@21899635）；② 插件级：`const ready = loadLedger()`（index.js:181）内部由 `try/catch/finally` 全包且 `finally { ledger.loaded = true }`，**`ready` 结构上不可能 reject**，因此不产生"插件自制未处理拒绝"的路径；③ 隔离实测：以 Fake ctx 在 Node 里裸跑 `apply(ctx)` → 无异常，4 个 effect / 3 条路由全部注册（§5.1）。

**附带结论（P1 之前最重要）**：当前磁盘上这份代码**已经在本进程里生效过**——purge 探针真实返回 200 且移除数量与谓词自洽（§5.3），即"重启后加载会失败"的概率被实测压到很低。

## 3. 隔离能力专节（§A 源码证据）

### A1 启动策略：非必需插件失败 → warning，继续启动（决定性）

`app.asar` **@22051690 附近**（`dsh-app-boot` 启动审计）：

```js
/**
* Apply DSH startup policy to a settled Loader tree.
*
* Inactive entries from the global required list reject startup. Other
* inactive entries join that failure diagnostic, or produce one warning when
* no required entry failed and leave successful siblings running.
* ...
*/
async function auditStartupEntries(ctx, binName, warn = (line) => void process.stderr.write(line)) {
	const failures = await inactiveEntries(ctx);
	const required = new Set(failures.filter(({ entry }) => entry === bootstrapIncludes.get(ctx) || requiredStartupEntryIds.has(entry.options.id)).map(({ entry }) => entry));
	if (required.size > 0) throw new StartupError(startupDiagnostic(binName, failures, required), ...);
	if (failures.length > 0) warn(activationDiagnostic(binName, failures));
}
```

必需清单（**@22044494**，全 asar 仅此一处定义，@22052091 为使用点）：

```js
const requiredStartupEntryIds = new Set([
	"agent-loop", "webserver", "web-runtime", "modules",
	"connection", "headless-runner", "acp", "sdk-jsonrpc-server"
]);
```

→ 本插件行 `id: dsh-tok-rate` 不在其中，故失败 = warning-only。

### A2 插件行能否标记 optional / required？——**不能，也不需要**

`dsh-tok-rate/cordis.patch.yml` 全文（证物）：


**没有任何 optional/required 字段可写**：是否"必需"由宿主内建 id 白名单（A1）决定。本插件 id 撞不上白名单 → 天然享受降级保护。插件 `package.json` 里也没有控制项（`dsh.bundle.patch` 只声明 patch 文件）。

### A3 双闸门：装载期"整行跳过" + 启动期"warning 放行"

`loadProfileDirectory()`（**@21899635**）——装载期：

```js
for (const packageName of bundles) try {
```

### A5 前端 bundler 的旁路隔离

| P1 改动 | 启动期风险 | 改之前必须验什么 |
|---|---|---|
| 1. 均值改中位数（`aggregateEntries`，index.js:78-112） | **否**（纯函数；空账本返回 `[]`） | ① 空账本 / 全 `timingSuspect` / 全非对象条目三种边界不抛；② 字段名变更要同步改前端（client 消费 `avgTps`），否则 UI 报错但不影响宿主 |

## 9. 一句话总结

**重启不会因为 dsh-tok-rate 起不来**：宿主对非必需插件行有**装载期（跳过 bundle）+ 启动期（warning 放行）**双重隔离，本插件 id 不在必需白名单；插件自身在 import 期与 `apply()` 期都无可抛错的顶层语句与阻塞 IO，`ready` 结构上不可能 reject，1.1 MB 账本加载成本仅 **4.5 ms**。最可能的现实后果是**插件自己静默失效**（账本损坏 → 改名降级；bundle 解析失败 → 整行被跳过），表现为 stderr 一行 warning + UI 里 tok/s 不刷新。回滚清晰且 30 秒可完成（改 `cordis.patch.yml` 名字 或 从 `bundles` 删除），官方插件页还支持直接取消勾选。

**唯一未穷尽的缺口**是 U1（真正的冷启动实测）——本任务禁止重启宿主；建议 lead 在用户下次自然重启后用 U1 的两条命令做 30 秒复核。
