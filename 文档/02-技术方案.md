## 1. 一句话目标

做一个 DSH 插件，在**当前会话**里以 ≤200 ms 的节奏实时显示模型调用速率——**tok/s、首 token 延迟（TTFT）、每分钟请求数（RPM）、上下文占用增长**——数值必须可被官方 `usage` 校准对账，而不是纯猜。

## 2. DSH 插件机制事实清单（本节全部实证，逐条给证据）

### 2.0 一句话总纲

> DSH 是 **Cordis 插件树**宿主：每个插件 = 一个 npm 包，导出 `name` / `inject` / `Config` / `apply(ctx, config)` 四件套；包内用 `package.json` 的 `dsh.bundle.patch` 把插件插进 profile 的插件层栈，用 `dsh.client` 声明「我还带一个浏览器端 bundle」。宿主提供 `llm/stream` 这类 **waterfall 中间件**，可以在模型请求/流式 chunk 层做拦截——**这就是实时速率的数据源头**。

### 2.1 插件形态：本机可证实的共 2 类「代码形态」+ 1 类装配形态

| # | 形态 | 是什么 | 证据 |
|---|---|---|---|
| A | **宿主侧（Node）插件** | 跑在 DSH 宿主进程里，能 `ctx.on()` 挂事件、注册工具、注册 HTTP 路由 | 见 2.1.1 |
| B | **client-plugin（浏览器端 UI 插件）** | 打进 `lib/client.js`，由宿主按 `dsh.client.platform: "web"` 加载，在浏览器里 `ctx.slots.register(...)` 渲染 UI | 见 2.1.2 |
| C | **bundle（装配层）** | 不是代码形态，是把 A/B 塞进 profile 插件树的清单机制 | 见 2.1.3 |
| D | skill | `~/.dsh/skills` 下的技能包 | 本机存在，但**本次未核实清单字段** → `[未验证]` |
| E | command / statusline | 命令行 / 状态栏插槽 | **本机未取到任何证据** → `[未验证]`，不得在实现里假设其存在 |

### 2.2 插件能挂哪些 hook / 中间件（本节最关键）

#### 2.2.1 `llm/stream` — waterfall 中间件，模型请求的总闸门

**结论**：宿主每次发起一次模型流式调用，都会走 `llm/stream` 这个 waterfall，中间件签名 `(options, next) => Promise<AsyncIterable<StreamChunk>>`，**必须 `return next()` 委托**，否则会掐断模型调用。

**证据 H1** `[真插件源码]` `injector/src/index.ts:259-263`

```ts
  // 观察面：捕获主模型路由（waterfall 必须 next() 委托）
  ctx.on('llm/stream', (options, next) => {
    lastRoute = { provider: options.provider, model: options.model }
    return next()
  })
```

#### 2.2.4 `usage` 的真实字段名（token 统计点）

**结论**：usage 对象是 **`{ inputTokens, outputTokens, cacheReadTokens?, cacheWriteTokens? }`**（camelCase，**不是** `prompt_tokens` / `completion_tokens`——那两个是 OpenAI 线格式，只在直连 provider 的原始响应里出现）。cache 字段**仅在 >0 时存在**。

**证据 H5** `[宿主源码]` 同文件 `:1249-1263`

```js
/**
* Map pi-ai usage (reasoning folded into output by pi-ai).
* @param usage - cumulative usage from the terminal pi-ai event.
*/
function mapUsage(usage) {
  return {
    inputTokens: usage.input,
    outputTokens: usage.output,
    ...usage.cacheRead > 0 ? { cacheReadTokens: usage.cacheRead } : {},
    ...usage.cacheWrite > 0 ? { cacheWriteTokens: usage.cacheWrite } : {}
  }
}
```

**关键限制**（决定整个设计）：**准确 token 数每个请求只在流末尾给一次**。所以「实时 tok/s」只能由 delta 的字符量与到达时间推算，再用结尾的 `usage.outputTokens` 反算校准比率——这是唯一同时满足「实时」与「可对账」的路线。

## 4. 推荐方案

**选 方案 B：宿主侧 `llm/stream` 拦截 + 自注册 HTTP 快照接口 + 客户端 `conversation.input.dock` 常驻速率条**，并保留方案 A 的**字符估算**作为唯一不可省的部分（因为真 token 数每秒拿不到）。

### 4.1 为什么是它

1. **唯一同时满足四件事**的路线：实时（chunk 级）、可对账（每请求末尾真 `usage`）、会话归属正确（`sessionId`）、不碰宿主文件系统（避开 S3 那条崩溃路径）。
2. **改动面最小且边界干净**：宿主侧一个 `apply` 里挂 2 个东西（`ctx.on('llm/stream')` + `ctx.webServer.register`），客户端一个 dock 组件。不改 DSH 检出、不改官方 UI、不做 DOM 注入。
3. **不需要重建 web 产物**、开发期可用 injector 热重载（L1/L2），迭代成本低。
4. 已被生态验证：本队前序扫描（`[二手]`）记录 `better-er/dsh-live-token-stats` 走的正是「宿主拦截 `llm/stream` + 自注册 RPC」，说明这条路在同一宿主版本上跑通过。

### 4.2 第一版做 / 不做 / 以后做

| 阶段 | 内容 |
|---|---|
| **第一版做（MVP）** | dock 常驻条：`tok/s`（含思考合并）、本请求 `TTFT`、当前会话 `RPM`（60 s 滑窗）、上下文占用（最近一次 `inputTokens+cacheReadTokens`）；每请求结算后与官方 `usage` 对账并在悬停里显示偏差；无数据/错误态；按 sessionId 隔离；设置项（开关、采样窗口、dock 排序）|

## 6. 数据采集设计（落到「监听哪个事件 / 读哪个字段 / 怎么算」）

### 6.1 监听点

| 目的 | 接口 | 关键字段 |
|---|---|---|
| 请求开始 / 计数 | `ctx.on('llm/stream', (options, next) => ...)`（H1） | `options.sessionId`、`options.provider`、`options.model`、`options.maxTokens` |
| 逐 delta 到达时刻 | 同上，`for await` 消费 `next()` 返回的 `AsyncIterable<StreamChunk>`（H3） | `chunk.type ∈ {block-start, text-delta, reasoning-delta, tool-call-delta, block-end, usage, finish}`；`chunk.text` / `chunk.blockType` / `chunk.argumentsDelta` |
| 真 token 结算 | 同上，`chunk.type === 'usage'`（H5） | `chunk.usage.outputTokens` / `.inputTokens` / `.cacheReadTokens?` / `.cacheWriteTokens?` |
| 结束 / 原因 | 同上，`chunk.type === 'finish'` | `chunk.reason`（成功/失败/中断/超长） |
| 推给浏览器 | `ctx.webServer.register({ kind: 'prefix', path: '/dsh-rate/api' })`（H9/H10） | 自己定义 JSON 快照 |

> **实现纪律**：中间件必须 `return next()`；对 chunk 流的消费必须是**旁路观察**——把 `next()` 返回的可迭代对象包一层 `async function*`，`yield` 原样透传，绝不吞 chunk、绝不改内容。这是本插件唯一能弄坏模型调用的地方（对应 §9 风险 1）。

### 6.2 每个 session 的状态机（内存态，不落盘）

```
state = {
  sessionId,
  requests: [ { reqId, startedAt, firstDeltaAt|null, lastDeltaAt, chars, finishedAt, usage|null } ],  // 仅保留最近 60 s 窗口
  charsPerToken: 2.0,        // 校准后的比率，初始取保守值
  phase: 'idle' | 'waiting' | 'streaming' | 'tool' | 'settled' | 'error',
}
```

阶段推导（只用 chunk，不依赖未验证的事件名）：
- 收到 `llm/stream` → `phase='waiting'`，计时开始（这是 **TTFT 的 t0**）。
- 第一个 `text-delta` 或 `reasoning-delta` → `phase='streaming'`，记 `firstDeltaAt`（TTFT 定格）。
- 出现 `block-start(blockType='tool-call')` 且期间无 text/reasoning delta → `phase='tool'`（冻结速率，不产生 0 碎点）。
- 收到 `usage` → 记结算；收到 `finish` → `phase='settled'`。

### 6.3 速率算法

**实时 tok/s（唯一可用口径 = 字符估算 → 比率校准）**

1. **采样**：每 200 ms 读一次该 session 的 `chars`（`text-delta.text.length + reasoning-delta.text.length` 累计；工具调用 delta **不计**），得到样本序列 `(t_i, chars_i)`。
2. **滑动窗口**：2 s 窗口内 `Δt = t_now - t_windowStart`，`Δchars = chars_now - chars_windowStart`；
   `est_tps = Δchars / charsPerToken / max(Δt, 0.25)`（分母下限 0.25 s，防首包尖峰，这是生态通用做法）。
3. **平滑**：对 `est_tps` 做 EWMA，`α = 0.3`（`rate = 0.7*prev + 0.3*new`）——采样率 5 Hz 下等效于 ~0.5 s 时间常数；比 0.5 s 窗口更抗抖动，又不会糊掉节奏。
4. **冻结规则**：`phase ∈ {waiting, tool, idle}` 时**不产生样本**（不是产生 0），UI 显示状态词而非 0。
5. **校准（关键）**：每次 `usage` 到达时，用该请求的 `observedChars = chars_at_finish` 与 `usage.outputTokens` 反算 `cpt_observed = observedChars / outputTokens`，然后
   `charsPerToken = clamp(0.9 * charsPerToken + 0.1 * cpt_observed, 0.3, 20)`；**只在 `outputTokens >= 50` 时校准**（小样本噪声太大）。
   `reasoning` 也被 `outputTokens` 包含（H5 注释：`reasoning folded into output`），所以正文+思考**合并计数**才是与 usage 同口径的；双线曲线只能显示分线占比，总量仍用合并值。

**TTFT**：`firstDeltaAt - requestStartedAt`（首个 text **或** reasoning delta，两者都算「模型开始出字」）。等待期间 UI 用同一时钟**实时爬升**（不是显示静止 0），这样「卡住」是可见的。

**RPM / TPM**：60 s 滑动窗口数 `requests[].startedAt` 落在窗口内的条数 = RPM；窗口内 `Σ outputTokens` = TPM。**这是当前会话口径**，与前序扫描确认的生态空白一致（`[二手]`：`dsh-metrics` 只有账户级 60 min，本机无竞品做会话级实时 RPM）。

**上下文占用**：`最近一次 usage.inputTokens + (cacheReadTokens ?? 0)`；分母取 `options.maxTokens` 不可靠（那是输出上限），容量需从模型目录取——**模型 catalog 接口名 `[未验证]`**，第一版若无分母就只显示绝对 token 数 + 增速（token/轮），不显示百分比。这与官方环状占用条不冲突（官方那个是另一条数据线，D2）。

### 6.4 宿主 → 浏览器

`GET /dsh-rate/api/snapshot?sessionId=<id>` 返回：

```jsonc
{ "sessionId": "...", "phase": "streaming", "tps": 42.3, "tpsSource": "estimated",
  "ttftMs": 812, "ttftLive": false, "rpm": 3, "tpm": 1240,
  "contextTokens": 18432, "lastSettled": { "tps": 38.9, "outputTokens": 720, "estimatedTokens": 745 },
  "ts": 1793008286855 }
```

- 轮询而非推送：**10 Hz 只在 `phase === 'streaming'` 时**，其余 1 Hz，空闲 0.2 Hz。理由：宿主侧 SSE/WebSocket 推送能力 `[未验证]`，而同源 HTTP 轮询有 H9/H10 两个真插件背书；10 Hz × 小 JSON 在本机 loopback 上是噪声级开销。
- 路由必须同源校验（照抄 H10 的 `sameOrigin`/`trustedDownloadRequest` 思路），只服务 `127.0.0.1`。

## 7. 实时展示设计

- **位置**：`conversation.input.dock`，`order: 10`（夹在宿主 todo dock `order:0` 之下、queue dock `order:20` 之上——U1/U2/U3 实证这些 order 的用法）。理由：这是本机唯一实证的「输入框上方常驻横条」槽，且天然按会话作用域注入（`inject(sessionId)`）。

- **刷新频率**：数据 10 Hz（仅生成中）；DOM 更新用 `requestAnimationFrame` 合帧，**数字最多 5 Hz 变**（人眼在 10 Hz 上读数字只会抖）。绝不触发会话树重渲染——组件只订阅自己的快照。
- **状态矩阵**：

| 状态 | 显示 |
|---|---|

## 9. 风险与待澄清问题（按影响面排序，≤5）

1. **`options.sessionId` 是否真的到达中间件**（影响面：整个会话归属，方案 B 的地基）。
   已证：provider adapter 收到 `options.sessionId`（H2, adapter:1742）。未证：`ctx.on('llm/stream')` 中间件拿到的 `options` 是同一对象。
   缓解：S1 一条探针即可判定；若拿不到，退化路径是**在中间件里用 cordis 上下文/agent 反查 session**（`context.agent.session`，H6 已证存在），代价 +2 h。
2. **`conversation.input.dock` 是否对第三方插件开放**（影响面：UI 位置，能不能「常驻」）。
   已证：宿主自己往里注册两个 dock（U2/U3）。未证：槽是否有 owner 限制。
   缓解：S1 用探针实测；失败则退化到 `conversation.composer.bar`（U1 已证槽名）或 `conversation.view` 标签页，再不行退 `settings.section`。
3. **没有官方 tokenizer，实时值必然是估算**（影响面：数值可信度）。
   `[未验证]` 宿主是否暴露 `countTokens` 之类 API（本机未取到）。第一版接受「估算 + 每请求末校准」，并在 UI 上明示 `estimated`/`settled` 两种口径，**不把估算值伪装成计费值**——这是本队前序验收里反复强调的度量纪律。
4. **插件必须重启宿主才生效**（影响面：迭代速度 + 用户打扰）。
   本机有 supervisor 守护并设了 1500 MB 内存阈值自动重启（`[二手]` DSH-STABILITY-NOTES:405-436），重启会中断进行中的会话。缓解：开发期用 injector 的 `dev_reload_package` 热载（L2）；发布期在 README 明确「装完重启一次」。
5. **`sessionStats`/`tokenUsage` 投影 face 名未在本机确认**（影响面：上下文占用分母、与官方数字对账的便利性）。
   缓解：不作为 MVP 依赖；只在 v2 用它做二次对账。若 face 可用，F6 可从「只显示绝对值」升级为「显示百分比」。

## 10. 明确不做什么

1. **不修改 DSH 检出目录**（`resources/app.asar/dsh/`）任何文件；不做 asar 补丁、不覆盖官方 `StatsPills`。
2. **不做代理拦截**（方案 C）：不要求用户改 provider `baseURL`、不引第三方端口/证书。
3. **不读 `session.jsonl.zstd` 做实时源**：本机已有「5 秒全量扫描 → native zstd OOM → 宿主周期性崩溃」的实测事故（S3），此路禁止。
4. **不做 DOM 注入**：不往官方会话统计胶囊上打补丁（生态里 `suufon/dsh-turn-speed` 走这条，脆弱且随宿主改版即碎）。
5. **不做成本/价格估算**：缺权威价格表，宁可不算也不给错数字。
6. **不做跨会话历史持久化与排行榜**（v2 再说）；本插件不落盘任何统计。
7. **不硬编码未验证的 API 名**：`turn/start`、`step/end`、`assistant/message`、`sessionStats`、`tokenUsage`、模型 catalog 接口名——一律在 forge 阶段 grep asar 确认后再写进代码；本文档里凡标 `[未验证]` 者不得直接采信为契约。
