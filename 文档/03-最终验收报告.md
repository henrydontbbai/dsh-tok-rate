### Hunk 1（原 :413 → 新 :413-420）：把 (a) 类陈旧断言翻转，但**保留判别力**

```diff
-ok(h4.timingSuspect === undefined && h4.lowConfidence === true, 'FIXED: a realistic 100-token paused response is lowConfidence, NOT timingSuspect (reason ' + h4.lowConfidenceReason + ')')
+// P1-sem: this used to demand `timingSuspect === undefined`, i.e. the mutual
+// exclusion the final semantics removed. …
+ok(h4.timingSuspect === true && h4.lowConfidence === true, 'P1-sem: a realistic 100-token paused response carries BOTH marks (reason ' + h4.lowConfidenceReason + ')')
```

理由：
1. 旧断言编码的是**被取代的「互斥」设计**（(a) 类），在当前语义下**必然**失败（实测 `tps=1639.3~2173.9`，恒 >1000）。
2. 我**没有**把它改成「删掉/跳过」——那是修改验收资产、抹掉回归网。改成 `both === true` 后：
   - 正面要求「该 shape 必须同时带两标记」，与定稿公式一一对应；
   - 一旦有人把突发规则重新挂回 `!lowConfidence`（回退到旧语义），这条会**立刻红**——即它同时是**防回退探针**。
3. 与之配对的既有断言 `ok(h4old.timingSuspect === undefined && h4old.tps < 100, 'PRE-P1: … ~24 tps …')` **保持不变**（它验证的是 PRE-P1 模块的正确性，不受本轮影响）——实跑仍绿。

### Hunk 2（原 :420 → 新 :424-436）：修掉 (c) 类自身 bug，并加两条口径断言

```diff
-eq(hi.json.rows.reduce((s, r) => s + r.samples, 0), allEnts.length - hi.json.excluded - hi.json.lowConfidence, 'aggregate sample count == rows with neither mark (suspect AND low-confidence rows are excluded)')
+const dualMarked = allEnts.filter(e => e.timingSuspect === true && e.lowConfidence === true).length
+const disjointExpected = allEnts.length - hi.json.excluded - hi.json.lowConfidence
+console.log('  /history counters: excluded=' + hi.json.excluded + ' lowConfidence=' + hi.json.lowConfidence
+  + ' dual=' + dualMarked + ' disjoint-formula-would-say=' + disjointExpected)
+ok(hi.json.excluded === allEnts.filter(e => e.timingSuspect === true).length, '/history.excluded == timingSuspect rows on disk (stable under the new semantics)')
+ok(hi.json.lowConfidence === allEnts.filter(e => e.lowConfidence === true).length, '/history.lowConfidence == lowConfidence rows on disk (new counter)')
+eq(hi.json.rows.reduce((s, r) => s + r.samples, 0),
+  allEnts.filter(e => e.timingSuspect !== true && e.lowConfidence !== true).length,
+  'aggregate sample count == rows with NEITHER mark (union of the two marks excluded)')
```

理由：
1. **减式在重叠行上重复扣**：`excluded` 与 `lowConfidence` 是两个**可重叠的集合**，直接相减会把「两标记同时为真」的行扣两次。实测该 home：`total=4 excluded=1 lowConfidence=4 dual=1` ⇒ 期望值算出 `-1`（**负数样本数**，物理不可能），而真实聚合 `sampleSum=0` —— 这正是实现者指称的第 420 行「减式重复扣重叠行」bug，**裁定属实 (c) 类**。
2. 我把期望改成**并集口径**（直接数「既无突发也无低置信」的行），并对 `excluded`/`lowConfidence` **各自**加了一条与磁盘独立的对账断言 ⇒ 修 bug 的同时把「两个计数各自正确」也纳入回归网（旧断言其实没独立验证过它们）。
3. 保留 `console.log` 打印 `dual` 与「减式会给什么」⇒ 下次若同型 bug 复发，日志直接给出两个数字的对比（可读证据，而非只有断言名）。
4. 断言数变化：原 154+2 → 现 **158+0**（新增 2 条：`/history.excluded`、`/history.lowConfidence`；原 1 条 eq 拆为 1 条 eq + 2 条 ok），`pass` 从 154 变 158，失败 0。

## 6. 新发现

### 6.1 【实质 · 不阻塞重启】`MAX_ENTRIES=5000` 饱和后两条校准路径口径分叉

- **现象**（`.prove5/trim-probe.mjs`，我自造）：
  - 预置 4999 行干净样本（比值 5.0）→ 再灌 12 条比值 10.0 的新样本；
  - 内存态：`/history.total=5000`（已触发 `record()` 里的 `splice` 裁剪）但 `calibratedSamples=5011`、`charsPerToken=5.011973657952504`；
  - **重启后**：`recomputeCalibration()` 只能在磁盘上的 5000 行里累加 ⇒ `calibratedSamples=5000`、`charsPerToken=5.012000`；
  - **比值跳变 delta = +2.634e-05**（相对 5.2e-6，ppm 级）。
- **根因**（读码）：
  - `record()` 先 `push`，随后 `if (entries.length > MAX_ENTRIES) splice(0, n-MAX_ENTRIES)` 丢最旧行，
    但**同一函数里紧接着把 `calibratedChars/Tokens/Samples` 累加了**——被丢弃的那批行已经进过累加器；
  - 而 `flushLedger()` 只持久化 `entries`（`{version, updatedAt, entries}`），**不持久化累加器**，启动时 `recomputeCalibration()` 从裁剪后的行**重算**；
  - ⇒ 两条路径在「裁剪边界」上算的**不是同一批行**。这正是任务书要求核的「重启后数字会跳变」类缺陷，只是在**另一个触发条件**（行数饱和）下出现。
- **影响**：`×10⁻⁵` 量级、仅在账本跨过 5000 行之后出现，且**重启后收敛**到账本口径（不会持续漂移）。
  表现上：弹窗里的「估算 chars/token」在重启前后会有一位末位抖动。**不构成重启阻塞**。
- **修法（给实现者，一行级，我没有改码）**：裁剪之后重建累加器，例如把 `splice` 那一段改成
  ```js
  if (ledger.entries.length > MAX_ENTRIES) {
    ledger.entries.splice(0, ledger.entries.length - MAX_ENTRIES)
    recomputeCalibration()          // 与重启路径同口径：把被丢弃的行从累加器里去掉
  }
  ```
  或按被丢弃行的 `chars/outputTokens` 做减法（需连同 `timingSuspect/lowConfidence` 守卫一起减）。修完建议在 harness 里固定一条「跨 5000 行重启比值不变」的断言。
- **当前账本状态**：真账本 4853 行，**已在该边界附近**（约 147 行后进入该状态）。

### 6.2 【cosmetic】`lowConfidenceReason` 的 `decode-too-short` 分支在现实时序下几乎不可达

- 读码：`idleDominated = idleMs > wall*0.5`；`lowConfidence = decodeMs<=0 || (idleDominated && decodeMsEff<MIN_DECODE_MS)`；
  而 `reason = (decodeMs<=0 || idleDominated) ? 'idle-dominated' : 'decode-too-short'`。
- 由于 `decodeMsEff < 200` 时几乎必然伴随 `idleDominated`（除非 wall 本身 < 200 ms），我的 9 个自造 shape 与实现者的用例都只产出 `idle-dominated`，
  从未产出 `decode-too-short`。**不是错误**（分支纯防御），但该文案实际上不可观测，读者可能误以为「跨度太短」会对健康短流生效。
- 建议：要么保留但在注释里点明不可达，要么在 `wall<200 && !idleDominated` 时也允许该分支（需要产品决策，不建议在收口轮动）。

### 6.3 【cosmetic】`/live` 对 2 个标记的处理不对称（设计如此，值得写进交付说明）

- `timingSuspect=true` ⇒ `settled=null`（不给假数字）；`lowConfidence=true` ⇒ 仍给瞬时速率 + `lowConfidence:true`（标记而非抹零）。
- 因此弹窗里「瞬时速率」会继续跳动，但**低置信样本不会进统计**；这与「账本留痕、统计干净」的定稿意图一致，只是用户需要被告知（见 §7）。

`Temp\p1fix-selftest.txt`（02:40）声称 110 checks 通过，但其内部记录的 `timingSuspect=undefined` 与当前代码在同一 shape 上必然产出的 `true` 矛盾

### 7.2 弹窗数字怎么读（均值 / 中位数 / 低置信计数）

1. **先看中位数，再看均值。** 中位数是主数字：本机历史数据里均值被右长尾（代理批量下发、非流式突发）抬高 6~11%，
   所以「中位数 < 均值」是**正常**的，相差越大说明长尾越重。
2. **p95 / 截尾均值是稳健性参照。** p95 告诉你「最快的 5% 有多快」（常被突发拉高）；截尾均值把两端各 5% 去掉后重算，
   如果它接近中位数而远离均值 ⇒ 均值被尾部污染，别拿均值下结论。
3. **两条脚注是排除清单，不是限速：**
   - 「已排除 N 个非流式样本」＝ `timingSuspect`（`deltaChunks<3 && tokens>40`，或 `tps>1000`）：**一跳到底的突发**，不可用于比较速率；
   - 「M 个低置信样本」＝ `lowConfidence`：**停顿主导（idle > 墙钟一半且有效跨度 <200 ms）或成功跨度 ≤0**，即「这段速率测不准」。
   - **两者可同时命中一行**（同一行既可能「一跳到底」又「测不准」），所以两行的数字**不能相加当成被排除行数**——要看「未进统计」的真实行数请用 `total − 干净样本数`。
4. **`tps` 的分子是供应商自己的 usage 计数**（`outputTokens`），分母是本插件测量并扣除停顿后的有效跨度；
   1 次 `llm/stream` = 1 个样本，工具执行时间与同一轮的其他请求是**各自独立**的样本。
5. **chars/token**：本机校准值会随干净样本滚动画收敛（默认 1.7 起），只用于「还没拿到 usage 时」的估算显示（`estimated: true`），
   **估算值从不进账本、不进统计**。
