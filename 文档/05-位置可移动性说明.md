## 1. 直接回答（先看这里）

**位置能换，但不能"自由摆放"；"拖到任意位置"需要另起一套浮层，代价明显。**

三句话把机制说透：

1. **插件的位置 100% 由注册时的 `name`（插槽名）决定，`order` 永远挪不出插槽。**
   证据（`SlotCore` 的注册实现，asar `@105183301`）：
   ```js
   register(e,t){const r=this.records.get(e.name);
     if(!r?.spec)throw new Error(`slot "${e.name}" is not declared (a parent entry's children table must declare it)`);
   ```
   即：`name` 必须命中宿主**已声明**的插槽；`order` 只进入"该插槽自己的条目数组"的排序，渲染侧也是同一回事（`@26972302`）：
   ```js
   let list = [...rows].sort((a, b) => a.order - b.order);
   if (opts?.only !== void 0) list = list.filter((item) => item.id === opts.only);
   ```
   这段代码在 `renderOutletContent(host, slotKey, …)` 内，全部按 `slotKey` 取数 —— **跨槽移动只能靠改 `name`**。

2. **前序结论「`conversation.composer.dock` 拿不到 sessionId」是错的**（本轮已复核推翻）。
   `renderSlot("conversation.composer.dock", {})` 确实传空 ownerProps（`@25077669`），但该槽声明为 `kind:"list", scope:"session"`（`@24867325`），**session 作用域会把 `sessionId` 作为「标准 props」自动注入**，与 ownerProps 无关：
   - `runInject(entry, binding, actions)` 把 scope binding 的 key 作为 `inject` 的第一个实参（`@26939011`）：`const args = []; if (binding !== void 0) args.push(binding.key);`
   - `BUILTIN_SOURCE = { hooks:["session"], keyedHooks:["projection"], props:["sessionId"], … }`（`@27460406`）→ `materializeStandardBinding(binding) { const standard = { ...binding.props } … }`（`@26948269`）
   - 官方实证：`ui-open-in-app` 注册进 `conversation.session.header.utilities` 的组件签名就是 `function SessionOpenInAppAction(props){ const { sessionId, useSessions } = props; … }`（`@25961700` 段），而该槽渲染时同样是 `renderSlot("conversation.session.header.utilities", {})`（`@25020509`）。
   → **任何 `scope:"session"` 的槽，换过去都不会丢"按会话隔离"。**

3. **`position:fixed` 能逃出宿主容器裁剪**（静态证据充分）：祖先链上有 `overflow:hidden`（`.mP3x-q_frame`、`.mP3x-q_centerCol`、`.an3WzG_root[data-phase=active]`），但**没有任何祖先带 `transform` / `filter` / `backdrop-filter` / `contain` / `will-change` / `perspective`**（我把 `.an3WzG_*`、`.mP3x-q_*` 全量 CSS 规则扫了一遍，无一命中）。`overflow:hidden` 只有在祖先成为 fixed 元素的包含块时才裁剪它，所以 `position:fixed` 元素以视口为包含块、**逃逸成功**。而当前的弹窗是 `position:absolute`（`client.js:409`），父级 `composerSeat` 是 `position:sticky`（定位元素）→ 会被滚动/溢出祖先裁掉（设计规格 §0.3/§5.7 已经撞到过这个现象）。「浮层被裁」是 `absolute` 的问题，不是 `fixed` 的问题。

**结论**：想换固定位置 → 改 `name`（做法一）；想只调上下顺序 → 改 `order`（做法三）；想任意摆放 → 只能走浮层（做法二），可行但要付代价。**推荐做法一，落点 `conversation.session.header.utilities`**（会话标题栏右侧），理由见 §5。

### A1. `ctx.slots.register({name, id, order}, Component)` 各字段的作用边界

| 字段 | 作用 | 边界（关键） | 证据（asar 字节偏移） |
|---|---|---|---|
| `name` | **决定位置**。插槽名必须已被某个父条目的 `children` 表声明 | 没声明就抛错，不是"软失败" | `@105183301`：`if(!r?.spec) throw new Error(\`slot "${e.name}" is not declared (a parent entry's children table must declare it)\`)` |
| `id` | `list` 槽的**单元格键**（cell key）；同 id 同 priority 重复注册直接抛错 | 同 id + **不同 priority** = 遮蔽（shadow），**低 priority 胜出并渲染** | `@105183301` 段：`case"list":{ if(e.id===void 0)throw new Error(…requires options.id); const h=r.entries.find(p=>p.options.id===e.id&&(p.options.priority??0)===n); if(h)throw new Error(\`… already has an entry with id "${e.id}" … register at a different priority to shadow it (lowest renders)\`) }` |

| `priority`（清单外但决定性） | 与 `order` 正交的**遮蔽轴**，数字越小越优先/越先渲染 | 想替换别人的一个 list 条目 = **同 id + 更低 priority** | 同上 + 渲染侧 `@26972302` |

### A3. 哪些插槽能拿到 sessionId？（决定换位置后会不会串会话）

**判据：看该槽的 `scope`。`scope:"session"` ⇒ 100% 拿得到 sessionId（两条路：`inject(sessionId)` 实参 + 组件 `props.sessionId`）；`scope:"root"` ⇒ 拿不到，只能自己去根级服务读"当前会话"，也就放弃了"每会话各自读数"。**

机制证据：
- `inject` 的第一个实参 = scope binding key：`function runInject(entry, binding, actions){ … const args=[]; if(binding!==void 0) args.push(binding.key); … return bindInjectSources(inject(...args)) }`（`@26939011`）
- session scope 的标准 props 里含 sessionId：`const BUILTIN_SOURCE = { hooks:["session"], keyedHooks:["projection"], props:["sessionId"], resolve:(binding)=>({ … props:{ sessionId: binding.sessionId } }) }`（`@27460330` / `props:["sessionId"]` 在 `@27460406`）→ `materializeStandardBinding(binding, optional, defaultKey){ const standard = { ...binding.props }; … }`（`@26948269`）
- 官方实证（第三方可照抄）：`ui-open-in-app` 在 `conversation.session.header.utilities` 注册的组件直接解构 props 里的 sessionId —— `function SessionOpenInAppAction(props){ const { sessionId, useSessions } = props; const cwd = useSessions((state)=>state.byId[sessionId]?.cwd); … }`，注册点 `ctx.slots.inject("conversation.session.header.utilities", () => ctx.slots.register({ name:"conversation.session.header.utilities", id:"open-in-app", order:-10, locale:NS, inject: directoryInjected }, SessionOpenInAppAction))`（`@25961930` 段），而该槽渲染实参就是 `{}`（`@25020509`）。

**能拿 sessionId 的槽**（scope=session / session-maybe，本轮已逐一核对声明）：`conversation.input.dock`、`conversation.composer.dock`、`conversation.input.left`、`conversation.input.right`、`conversation.input.overlay`、`conversation.session.header.utilities`、`conversation.session.header.actions`、`conversation.session.header.corner`、`conversation.session.header.lineage`、`conversation.input.model`、`conversation.input.activity`、`conversation.input.permission`、`conversation.input.plan`、`conversation.chat.turnTail`、`conversation.view`。

**拿不到 sessionId 的槽**（root）：`shell.overlay`、`shell.bottom`、`shell.leading`、`sidebar.*`、`settings.*`、`main`、`rightbar`。

**复核结论（明确推翻前序）**：`conversation.composer.dock` 声明为 `{kind:"list", scope:"session"}`（`@24867325`），**能拿 sessionId，不会串会话**。前序把 `renderSlot(...,{})` 的空 ownerProps 误当成 sessionId 的唯一来源；实际 sessionId 来自 scope binding，与 ownerProps 无关。这也解释了为什么官方把它写成"给装饰/读数优先考虑的槽"。

### A4. 宿主容器 CSS 事实（决定浮层能不能逃出、会不会被裁）

DOM 祖先链（自插件根节点向上，逐级核实）：

| 层级 | 选择器 / 关键声明 | 是否裁剪后代 | 是否成为 fixed 包含块 |
|---|---|---|---|
| 插槽 outlet 包裹 | `const ANCHOR_STYLE = { display: "contents" }`（`@26968227`）；渲染为带 `data-slot="…"` 的元素 | 否（无盒子） | 否 |
| input.dock 的父容器 | `.an3WzG_composerStack{--dsh-composer-stack-gap:6px;gap:var(--dsh-composer-stack-gap);flex-direction:column;display:flex}` | 否 | 否 |
| 输入座位 | `.an3WzG_composerSeat{…}`；对话态 `z-index:7;background:linear-gradient(…);position:sticky;bottom:0` | 否（无 overflow） | 否（sticky 不建立包含块） |
| 对话体 | `.an3WzG_body{…;flex:1;min-height:0;display:flex;position:relative}` | 否 | 否 |
| 滚动体 | `.an3WzG_scrollBody{…;overflow-y:auto}` | 滚动裁，但不是包含块 | 否 |
| 对话根 | `.an3WzG_root{…;height:100%;display:flex;position:relative}` + `.an3WzG_root[data-phase=active]{overflow:hidden}` | **是**（overflow:hidden） | **否**（无 transform） |
| 中心列 | `.mP3x-q_centerCol{flex-direction:column;min-width:0;display:flex;overflow:hidden}` | **是** | 否 |
| 应用框 | `.mP3x-q_frame{…;height:100%;display:grid;position:relative;overflow:hidden}` | **是** | 否 |
| body | `body{margin:0;height:100vh;display:grid;place-items:center;isolation:isolate}` | 否 | 否 |

→ 祖先里有 3 层 `overflow:hidden`，但**没有一层带 `transform` / `filter` / `backdrop-filter` / `contain` / `will-change` / `perspective`**（已把 `.an3WzG_*`、`.mP3x-q_*` 全量规则扫过，零命中），所以 `position:fixed` 子元素以视口为包含块、**不被这 3 层裁剪**。

层叠注意：`composerSeat` 是 `z-index:7` 的层叠上下文，挂在其内部的 fixed 元素再高的 z-index 也只是"7 号层内部置顶"，仍会被 `[data-shell-overlay]`（`.mP3x-q_overlayLayer{position:absolute;inset:0;z-index:20;pointer-events:none}`）和宿主菜单（`z-index:1100`）盖住。

**顺手修正前序设计规格 §0.3 的一处归属错误**：`.GRgSLq_dock{justify-content:center;align-items:center;gap:12px;max-width:100%;padding-top:4px;display:flex}` 属于 `InputBar.module.css`（asar 内自带 `//#region …InputBar.module.css.mjs` 标记，`@25051055` 段），对应 DOM 是 `@25077515` 的 `className: InputBar_module_css_default.dock, "data-composer-dock": true, children: [ renderSlot("conversation.composer.dock", {}), ContextMeter ]` —— 即 **composer.dock 的行容器**；`conversation.input.dock` 的父容器其实是 `.an3WzG_composerStack`（flex column）。这正好解释了 §0.3 观察到的"全宽横条感"：column + `align-items:stretch` 把子项拉满宽度，所以插件根节点必须自带 `width:max-content`。

## 4. 四种做法对照表

改动量口径：只算 `client.js`（若涉及 host 半另标）；本轮**未写实现代码**，行数是按现有结构估算的增删量级。

| 做法 | 能做到什么 | 做不到什么 | 改动量 | 风险 | 生效方式 |
|---|---|---|---|---|---|
| **① 换插槽**（改 `name`） | 换到任一**已声明**的固定位置；session 作用域槽保住会话隔离；4 个候选位可选（§3） | 不能任意像素摆放；不能跨会话保存"我上次拖到哪"；只能选宿主预留的位置 | **小**：`client.js` 3–6 行（`inject` 的槽名 + `register.name` + 必要时精简/调整 CSS 3–10 行），合计 ≈ **10–25 行 / 1 文件** | 低。唯一真风险是选到 single 槽（抛错）或 root 槽（丢会话隔离）——已用对照表排掉 | **刷新页面**（见 §C.8；宿主 HMR 轮询还会在 ≤500ms 内自动推新，见下） |
| **② 浮层可拖拽** | **真正任意摆放**（`position:fixed` 逃出 overflow 裁剪已证）；可记忆位置；视觉上"悬浮在 UI 之上" | 不会成为"宿主布局的一部分"：它永不参与排布、永远悬在内容上（会挡正文/输入框）；换机器/清缓存后位置丢（localStorage 级）；root 层叠会被菜单/overlay 盖 | **中**：`client.js` ≈ **60–110 行**（拖拽状态机 + pointer capture + clamp 到视口 + 位置持久化 + 弹窗改挂载点 + CSS 改 fixed）。若沿用官方座位 `shell.overlay` 还得处理"当前会话"读取，再加 ≈20 行 | 中。①遮挡正文/输入框（用户明确会恼）；②层级被盖（z-index 7 层内）；③与宿主"不要在宿主控件周围设计运动轨迹"的官方指引相悖；④`localStorage` 在隐私模式可能抛错（须 try/catch） | 刷新页面 |
| **③ `order` 可配置** | 保持原位，只调 **dock 内**与 todo/goal/queue/genui 的上下顺序（当前 30，最靠下） | 换不了位置，只是"上下挪一格"；对 single/keyed 槽**完全无效**（实现里 order 不参与非 list 排序） | **小**：若只存 localStorage + 重注册 ≈ **25–40 行**；若走宿主设置体系（`settings.general.item` + `configForms`）另加 host 半 ≈ **40–70 行 / 2 文件**（本插件 host 半目前**零** settings 管线：`index.js:18 export const inject = ['webServer']`，无 `configForms`） | 低（重注册=先 dispose 旧的再 register，需保证不闪、不重复挂载） | 刷新页面（设置项本身即时生效） |
| **④ 保持现状** | 什么都不动 | — | **0** | 无 | — |

**为什么"固定位置"在插槽体系下其实是合理默认（做法四的辩护）**：
1. 宿主的设计意图就是"**由槽决定位置、由 order 决定次序**"——每个 occupant 都不许自己决定坐标（连官方内置的 todo/queue/goal/统计胶囊都老实待在槽里）。
2. 插槽保证了布局是**响应式**的：窗口缩放、侧栏折叠、hero/embedded 两种形态切换时，宿主自己会重排；自定位浮层要自己处理全部边界（用户缩小窗口后浮层可能被推出可视区）。
3. 三方插件抢同一个视觉区域时，宿主靠 slot+order+priority 仲裁；自定位浮层会**绕过仲裁**，容易和别人的 UI 叠在一起。
4. 代价极低：用户若只是"觉得它在输入框上方碍眼"，换槽（做法①）就是 3 行；只有"必须能在屏幕上任意钉住"这个需求才值得上做法②。

## 5. §C 生效方式、启动期风险与铁律复核

> 说明：为满足"§C 必须交代清楚"，本节插在"四做法"与"推荐"之间；§6/§7/§8 对应任务书的 5/6/7。

### C.8 改 `client.js` 是否只需刷新页面？——**是。已运行时实测，不是推断。**

链条（全部拿到证据）：

1. **供包 URL 带 rev**：`const PLUGIN_ROUTE = "/plugins"`（`@22970599`）；`comboUrl(ids, rev) => `${PLUGIN_ROUTE}/??<id>/client.js&rev=${rev}``（`@22970600` 段）。
2. **rev 来自文件元数据**（不是内容 hash）：`function artifactRevision(baseline){ return framedHash("plugin-artifact",[String(baseline.mtimeMs),String(baseline.ctimeMs),String(baseline.size)]) }`（`@22970374`）。
3. **响应带一年 immutable 缓存**：`IMMUTABLE_CACHE = "public, max-age=31536000, immutable"`（`@22968373`），且 `bundleResource` 是按**完整 URL（含 rev）**查预构建响应的（`@23001135` 段）→ **rev 不变就一定是旧字节**。
4. **有 HMR 轮询在改 rev**：`@deepseek-ai/dsh-client-hmr`，`Config = z.object({ pollIntervalMs: z.number().step(1).min(1).default(500) })`（`@22782888`），`apply()` 里 `syncWatches()` + `setInterval(pollWatches, pollIntervalMs)`，检测到 mtime/ctime/size 变化就 `ctx.clientModules.rebuilt(id)`（`@22784200` 段），并把它通过 SSE `/plugins/events` 推给浏览器（`onRebuilt` → `sseData({type:"rebuilt", id, rev})`）。
5. **运行时实测**（本机 `http://127.0.0.1:52787`）：
   ```
   GET /plugins/events  →  200  content-type: text/event-stream
   data: {"type":"graph","graph":{"rev":"d1dc1d39d3a6","release":{"version":"0.2.1-rc.3","commit":"be72761"}, …}}
   …
   {"id":"dsh-tok-rate","url":"plugins/??dsh-tok-rate/client.js&rev=8b5847b2f334","rev":"8b5847b2f334","inject":[]}
   ```
   → HMR 传输**在本机确实挂着**，`dsh-tok-rate` 是它监视的一行。
6. **供给的字节 = 磁盘当前字节**：抓 `plugins/??dsh-tok-rate/client.js&rev=8b5847b2f334` → `200`、33950 B；与磁盘 `client.js`（33881 B）做 `cmp`：`cmp: EOF on '/tmp/d.js' after byte 33881`（前 33881 字节**逐字节相同**），差值只是 combo 侧另加的 sourceMappingURL 尾注。→ 服务端没有"启动时快照"的陈旧副本问题。
7. **编辑面 = 服务面**：`~/.dsh/profiles/desktop/node_modules/dsh-tok-rate` 是**符号链接**指向 `C:/Users/HHPC/Documents/dsh/dsh-tok-rate`（`readlink -f` 实测；md5 相同）→ 直接改工作区 `client.js` 即可，无需 `pnpm install`/重装 bundle。

**结论**：**只改 client 半 → 不需要重启宿主。** 通常连手动刷新都不需要（SSE 会在 ≤500ms 内推 `rebuilt`，浏览器侧 HMR 接收器重载该模块）；手动刷新也一定拿到新代码。**唯一例外**：若某个组合里没挂 `dsh-client-hmr`，rev 不会更新，刷新会命中 1 年 immutable 缓存 → 那时才需要重启宿主。本机当前不属此例（已实测 SSE 200）。

**注意**：这条只覆盖 `client.js`。若改动落到**宿主半 `index.js`**（例如做法③走 `configForms` 设置体系），那属于宿主行加载，**需要重启宿主**才生效。

### C.9 启动期风险（四种做法共同）——都不许进模块顶层 / `apply()` 同步段

- 四种做法的改动都发生在**浏览器半**，且真正的动作是 `ctx.slots.register(...)` 与 React 组件内部行为。
- **`apply()` 同步段只做注册是安全的**：现有代码就在同步段里 `dispose`-able 地注册（`client.js:641-667`），做法①③只是把 `name`/`order` 换掉。
- **明令禁止**（会重演前序 R1/R2 类风险）：模块顶层读 DOM / `getBoundingClientRect()` / `localStorage` / `matchMedia` / 挂全局监听器或定时器。做法②的定位与拖拽监听**全部放进组件**（`useEffect` 或 `ctx.effect`），`localStorage` 读写包 `try/catch`（隐私模式、配额都可能抛）。
- 宿主侧隔离性不变：本插件 id 不在必需清单里，失败只 warning、不阻启动（前序已证）；本轮方案不新增宿主行。

### C.10 铁律复核（现有四条硬约束）

| 铁律 | 做法①换槽 | 做法②浮层拖拽 | 做法③order 可配 | 做法④保持 |
|---|---|---|---|---|
| `getSnapshot` 返回 primitive | ✅ 不触碰 | ⚠️ **新增"位置"状态时最容易踩**：若加 `useSyncExternalStore`，`getSnapshot` 必须只返回 number/string（如 `revision`），**绝不能返回 `{x,y}` 对象**，否则引用不稳定 → React 报错/死循环（前序 R9 同源） | ✅ 不触碰 | ✅ |

## 6. 推荐

**推荐组合：做法①（换到 `conversation.session.header.utilities`）+ 可选做法③（在设置里给一个"位置"下拉）。第一版只做①。**

**为什么选①+ `conversation.session.header.utilities`：**

1. **它是"一行读数"在语义上最正的位置**：与它同族的 occupant 就是 `open-in-app`（一个动作胶囊，order -10），说明这个槽就是给"标题栏右侧的小控件"用的；`gap:8px`、`:empty{display:none}`，天然适合一个胶囊。
2. **常驻性最好**：只要会话 chrome 显示就在；不像 `input.right` 会被 activity 展开 hidden，也不像 `composer.dock` 位于输入卡片下方会被渐变遮罩/居中布局影响。
3. **不挡任何东西**：远离正文与输入框，不会与用户的输入操作争焦点（做法②最大的体验代价正好被规避）。
4. **会话隔离天然保住**：`scope:"session"` → `inject: sessionId => …` 拿到就是本会话 id，`props.sessionId` 同样可用（`@27460406` / `@25961930` 实证）。用户"不要串会话"的硬要求零成本满足。
5. **不需要动浮层/z-index/裁剪**：宿主自己负责布局，也不触官方那条"不要在宿主控件周围设计运动轨迹"的红线。
6. **改动最小、可逆**：3–6 行 + 少量 CSS 瘦身，随时改回。

**为什么第一版不做②（浮层拖拽）：**
技术上完全可行（fixed 逃逸裁剪已证），但它把"插件"变成"自绘窗口"：永久悬浮遮挡、层叠受 `composerSeat` 的 `z-index:7` 层内限制、位置持久化只到 localStorage、还要自己 clamp 视口与多显示器边界。**宿主官方笔记直接劝阻**（"do not plan a motion path around host controls"）。若用户明确要"能拖"，建议作为 **v2 opt-in**：默认仍停在标题栏槽内，用户点"浮动"才升级成可拖浮层（并且记忆位置）。

**为什么不做①→ `composer.dock`：** 它是官方推荐槽、也拿得到 sessionId，但容器是 `justify-content:center;gap:12px`，会把胶囊与内置 ContextMeter 并排居中，视觉上变成"输入框下方居中一行"；若用户要的就是"离输入框更近"，这是最省的第二选择，值得做成设置里的第二个选项。

**为什么不做④：** 只在"用户其实不在乎位置、只是嫌弃它长得像横条"时才是正解 —— 那是视觉问题（前序设计规格已给方案），不是位置问题。**若用户只是想让它别挡在输入框上方，①就是答案。**

## 7. 实施要点（选定做法后照做）

### 7.1 换槽（做法①）——三步，缺一不可
1. **`inject` 的槽名也要改**（`client.js:644`）：
   `ctx.slots.inject('conversation.session.header.utilities', …)` —— 只改 `register.name` 而忘改 `inject` 的第一个参数，注册回调**永不触发**（`inject(name, cb)` 是"该槽被声明时"才跑）。
2. **`register.name` 同步改**（`client.js:645`）；`id:'tok-rate'` 可保留（list 槽按 `id` 去 cell，与本槽现有 `open-in-app` 不冲突）。**新槽里 `id` 必须在 priority 0 上唯一**，否则抛"already has an entry with id …"。
3. **CSS 微调**：`headerUtilities` 是 `display:flex;gap:8px`（行盒），我们根节点已是 `inline-flex;width:max-content`（`client.js` §CSS 段），**大概率零改动**；只需确认高度/圆角与 `open-in-app` 邻近控件一致。

### 7.2 换到别的槽时的注意点
- **`composer.dock`**：容器居中 + `gap:12px`，会与 ContextMeter 并排；确认渲染门（`variant==="composer"`）在 embedded/hero 形态下的表现。
- **`input.left` / `input.right`**：`input.right` 的父组在 activity 展开时 `hidden`；`input.left` 与"+"按钮同排，注意不要挤压。
- **绝不选 single 槽**（`shell.bottom`/`shell.settings`/`conversation.session.header.corner` 等）：同 priority 再注册会抛错，且它们都已有人占位。
- **绝不选 root 槽**（`shell.overlay`/`sidebar.*`/`settings.*`）：丢会话隔离。
- **不要臆造槽名**：没在 `children` 表里声明过的名字 → `register` 抛 `slot "X" is not declared`。上线前可用宿主的 Slots inspect（`cordis_inspect_list` → `Slots.listSubTree`，见 `@50164856` 的 provider 描述）在线核对槽名与 props。

### 7.3 若追加做法③（order 可配）
- 最省：**client 侧 localStorage** + 记住顺序 + 重注册（`const dispose = ctx.slots.register(...)` 返回 disposer，改 order 时 `dispose()` 再注册一次；用 `useState` 驱动，避免闪动）。键名加插件前缀（如 `dsh.tok-rate.order`）。
- 想做成正式设置项：宿主已有 **`configForms`** 服务（`ctx.configForms.get(ns)`，见 `@24139397`：`chatSettings = ctx.configForms.get("ui-chat")`），配合 `settings.general.item`（list/root，`@30664913`，例如设置→通用那一行）。**但本插件 host 半目前零 settings 管线**（`index.js:18` 只有 `inject = ['webServer']`），要走这条路要动 host 半 → **需要重启宿主**。取舍：为"上下挪一格"付这个代价不划算。

### 7.4 若用户坚持做法②（浮层拖拽）
- 定位：`position:fixed` + 直接写 `left/top`（不要用 `transform`，一旦用了就自己把自己变成包含块，后续子元素/弹层定位会连带受影响）；拖拽用 Pointer Events + `setPointerCapture`，`pointerup/pointercancel` 都要解绑。
- 边界：拖动后 `clamp` 到 `window.innerWidth/innerHeight` 内；`resize` 事件后重新 clamp（否则缩窗后胶囊会飞出可视区）。
- 持久化：`localStorage`（`try/catch`），刷新与会话切换后保持。**注意 localStorage 是"页面级"而非"会话级"**：天然是"全局一个位置"，这通常正是用户想要的；想"每会话各自位置"要另存 sessionId→坐标映射，不建议。
- 层级：挂在 `composerSeat`（`z-index:7`）内 → 高于正文、低于 `[data-shell-overlay]`(20) 与菜单(1100)。**不要**去和宿主菜单抢 z-index。
- 弹窗层叠必须一起改：现弹窗 `position:absolute;bottom:calc(100% + 6px);left:0;z-index:40`（`client.js:409`）是挂在胶囊根上的；胶囊一旦 fixed，弹窗要么跟随（继续挂同一根、保持相对定位），要么改成随胶囊坐标走 —— **否则会出现"胶囊拖走了、弹窗还留在原处"**。
- 用户代价必须说清：它**永远悬浮在正文/输入框之上**，只能靠拖到边角规避；窗口变窄时会压住内容。建议默认仍停在槽内，只在用户显式开启"浮动"后才切换。

### 7.5 通用
- 改完 `node --check client.js`；先只改一处、刷新目视确认（本 GUI 会自动热更，注意别把"没刷新"当成"没生效"）。
- 不要动 `package.json`（`dsh.client.inject` 保持现状即可；槽只依赖 `ctx.slots`，不需要写进 `dsh.client.inject`）。
