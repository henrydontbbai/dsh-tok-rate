## 0. 三条生死约束（违反即返工）
1. **自动备份（P1-6）与凭证校验收紧（P1-4）绝不得进 import 期（模块顶层）或 `apply()` 的同步段**。顶层抛错会走 loadProfileDirectory 的 per-bundle try/catch → 整行被跳过 → 插件消失。
2. **`settle()` 加 try/catch（P1-3）必须保住 `finally` 里的 yield 通道与 `decoding` 复位**——否则异常会替换/吞掉正常完成或 provider 错误事件，破坏用户对话流。
3. **不得破坏既有铁律**：`getSnapshot` 返回 primitive（自增整数）、槽位 `conversation.input.dock`、无 `engines.dsh`、无 `@deepseek-ai/dsh*` peerDependency、只 `require('react')`、`options` 只读、`sessionId` undefined 有保护。

## 1. 七项改动

### P1-1 聚合口径 mean → median（约 25 行）
- 文件：`index.js`（`aggregateEntries`）、`client.js`（弹窗渲染）
- 实测依据：glm-5.3-flash mean 64.1 / median 57.8 / 5-95 截尾 60.8，**均值被长尾抬高 6~11%**；且账本 max 正好 = 1000.0，`tps > 1000` 严格大于刚好漏过边界样本。
- 动作：`aggregateEntries` 每组增加 `medianTps`、`p95Tps`、`trimmedMeanTps`（5-95 截尾）；**client.js 弹窗主数字改显示 median**，原 mean 降为副信息（保留字段，避免破坏其他读取方）。
- 验收：`/history` 返回含新字段；同组 median ≤ mean；用真账本复算与独立计算一致。

### P1-2 purge 改「归档 + 移除」（约 5 行）
- 文件：`index.js`（`purgeRoute`）
- 动机：purge 是**唯一不可逆**操作。已验证每清一次就永久损失证据（实测：清后 timingSuspect 又回到 15 条、`tps>1000` 回到 3 条；验收期间再清一次又 removed 32 条）。
- 动作：命中条目先 append 写入归档文件（如 `purge-archive-<ISO ts>.jsonl`，放在同一插件数据目录），**成功落盘后**再从 `ledger.entries` 移除；响应体增加 `archived: n`；归档写失败时**不删除**（宁可不清，不可先删后写）。
- 验收：调 purge 后归档文件存在且含被删条目；`archived` 数 == `removed` 数；归档失败路径不丢数据。

### P1-3 `settle()` / `noteDelta()` 加异常隔离（约 3 行）
- 文件：`index.js`（`index.js:358-360` finally 内的 settle 调用；`index.js:350` noteDelta 调用处）
- 动作：`try { settle(...) } catch (e) { ledger.saveError = String(e?.message ?? e) }`；noteDelta 同理。
- **必须**：不能改变 finally 内既有的 yield/return 语义与 `decoding=false` 复位；异常只能被记录，不得向外抛。
- 验收：构造一个会让 settle 抛错的输入（如 usage 字段类型异常），确认流仍正常结束、会话不卡在 decoding=true。

### P1-4 写路由凭证校验收紧（约 4 行）
- 文件：`index.js`（`allowedWriteRequest`）
- 现状（实测）：缺 `sec-fetch-site` 头时**放行** → 本机任意进程 `curl -X POST .../purge`（不带头）可静默清账本（实测 200）。
- 动作：**写守卫要求显式 `same-origin`**（缺头即拒）；**读守卫 `allowedRequest` 保持宽松不动**（避免破坏既有读路径：无头 GET 实测 200 是当前正常用法）。
- 验收：无头 POST /purge → 403；`sec-fetch-site: same-origin` POST → 200；无头 GET /history → 仍 200（不回归）。

### P1-5 空闲间隔从 decodeMs 分母剔除 + 官方口径对账（约 20 行）
- 文件：`index.js`
- 现状问题：分母含「代理攒批停顿」，导致 tps 系统性低估且无法自查；需求 §7 明写「若可得官方口径则优先对账」，代码里**零使用**。
- 动作分两步，**第 1 步必须做，第 2 步先验可行性**：
  1. **idleMs 单列**：统计相邻 delta 之间超过阈值（建议 ≥1000ms）的空闲墙钟，从 `decodeMs` 剔除或单列 `idleMs` 字段落账本；保证 `decodeMs` 反映真实解码时间。
  2. **官方口径对账（先验后用）**：第三轮复核称官方 `timing.completedTime - timing.firstTokenTime` 语义等价且已在 asar 取证。**请先确认从 `ctx.on('llm/stream')` 中间件能否取到该 timing 数据**（在 asar 里搜 `completedTime`/`firstTokenTime` 的使用位置，确认它是否出现在 chunk 或 options 上）。**能取到**才记 `tpsOfficial` 并算偏差；**取不到就在报告里明确写「不可达，已跳过」并说明验证方式**，不要臆造 API。
- 验收：账本新样本含 `idleMs`；若实现了对账则含 `tpsOfficial`；报告写明第 2 步的可行性结论与证据。

### P1-6 账本损坏自动备份回退（风险：不得进 import 期，见 §0-1）
- 文件：`index.js`（`loadLedger` 附近）
- 现状：账本损坏即历史归零；现有 `.bak*` 全是手工备份、非插件自建。
- 动作：**滚动自动备份 1–2 份**（如 `ledger.json.auto-bak-1/-2`，在成功加载/落盘后轮转）；`loadLedger` 检测到损坏时，把坏文件改名保留（`.corrupt-<ts>`）并**在 `loadError` 文案里指明可恢复来源**。
- **约束**：备份动作放在异步路径（`loadLedger` 内或 `flushLedger` 后），**不得**在模块顶层同步执行。
- 验收：自测里模拟坏 JSON → 插件不崩、坏文件被改名、loadError 提示可恢复来源。
